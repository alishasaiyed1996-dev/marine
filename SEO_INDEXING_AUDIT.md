# SEO indexing and page delivery audit

**Audit date:** 2026-10-20
**Scope:** repository code, generated frontend build, local HTTP behavior, and unauthenticated public HTTP responses using a Googlebot user agent.  
**Status:** code fixes are in the workspace and locally exercised. Production was still serving the old behavior when last checked. No production migration or deployment was performed.

## Executive findings

There is no single meaningful “total page” number because storefront routes include locale variants, user-only routes, admin routes, and one database-driven product route per published product. The current intended indexable inventory is:

- **13 English static pages** generated by `scripts/prerender-routes.mjs`.
- **One English URL per published product** from the database. The live storefront API reports **0 published products**. A read-only count against the local Neon direct connection returned **1 draft, 3 archived, and 0 published products**, but production uses a separate Railway Postgres database, so that breakdown is not production inventory.
- This means the intended sitemap target at audit time is **13 static URLs + the actual published product count plus eligible brand/category hubs**. Do not treat admin routes, account/checkout routes, search filters, or untranslated locale copies as indexable pages.

The React router has **25 storefront route patterns** under `/:locale/*` (including redirects and a catch-all) and **19 explicit admin route patterns**. Those counts describe code routes, not indexable URLs. Admin pages are protected except the login route and should remain noindex.

## Page delivery and code layout

### Request flow

1. A browser or crawler requests `alkatraders.co`.
2. The frontend Node process in root `server.js` handles canonical redirects and product requests, proxies `/sitemap.xml` to the direct backend API origin, then serves Vite assets and prerendered pages.
3. Product responses fetch data from `VITE_API_URL` (normalized to the API origin) and return product-specific HTML, title, description, canonical URL, Open Graph tags, and Product JSON-LD before React runs.
4. The API service in `backend/src/server.ts` mounts storefront and admin routes under `/api/v1` and reads products through Prisma/Postgres.
5. The product sitemap is generated by `backend/src/services/sitemapService.ts` from rows whose status is `published`. Admin publishing and product edits update the content timestamp through `backend/src/services/productMutations.ts`.
6. React hydrates the HTML for interactive filters, cart, account, and admin features. Search engines should not need hydration to discover the primary product title and body.

### Relevant source structure

- `server.js` — Node frontend entrypoint, redirect policy, product HTML route, runtime sitemap proxy, static assets, and SPA/prerender fallback.
- `src/App.tsx` — storefront, account, admin, and locale React route map.
- `src/pages/` — public and customer-facing pages; `src/pages/admin/` — admin screens.
- `src/components/seo/SEO.tsx` — client-side metadata and JSON-LD for hydrated routes.
- `scripts/prerender-routes.mjs` and `scripts/prerender.mjs` — generate the 13 English public static page shells and product shells when the build API returns products.
- `public/robots.txt` — crawler policy and sitemap URL. The legacy `public/sitemap.xml` was removed.
- `backend/src/routes/storefront/products.ts` — published product-by-slug and old-slug lookup.
- `backend/src/routes/storefront/sitemap.ts` and `backend/src/services/sitemapService.ts` — dynamic XML endpoint and its database-backed URL list.
- `backend/src/routes/admin/products.ts` and `backend/src/services/productMutations.ts` — protected product listing, editing, publish state, slug history, and content timestamps.
- `backend/prisma/schema.prisma` and `backend/prisma/migrations/20261019000000_product_seo_url_history/` — content last-modified field and previous-slug storage.

## Route inventory

### Intended sitemap pages

The 13 English static routes are `/en/`, `/en/products/`, `/en/industries/`, `/en/brands/`, `/en/about/`, `/en/rfq/`, `/en/contact/`, `/en/emergency/`, `/en/network/`, `/en/intelligence/`, `/en/privacy-policy/`, `/en/terms-of-service/`, and `/en/refund-policy/`.

Each published product adds `/en/product/{current-slug}/`. UUID URLs and previous slug URLs redirect to the current slug. Unknown products should return 404 with noindex. No filter URLs or account/admin URLs belong in the sitemap.

The React storefront has these route patterns: home, legacy shop redirect, products, industries, brands, about, RFQ, contact, search, emergency, network, intelligence, checkout, forgot password, reset password, order tracking, account orders, account offers, offer payment, profile, product detail, privacy, terms, refund, and not found. Arabic and Spanish route shells remain reachable but are explicitly noindex until translated content exists.

The 19 admin route patterns are login, dashboard, products list, eBay inventory, media, brands, industries, orders, customers, categories, RFQs, offers, messages, users, audit log, settings, insights, product creation, and product editing. They are operational pages, not search landing pages.

## Admin product listing: what exists and what to add

The current admin product list (`src/pages/admin/AdminProducts.tsx`) already has server-backed pagination (20 rows), search, filters for category/brand/condition/availability/status/sale/new arrivals, sorting, CSV export, import, and product editing. The form already exposes SEO title and description fields. The backend accepts SEO metadata and publishes products through protected admin routes.

The current system already has the right source-of-truth mechanism for automatic indexing: published database rows feed the dynamic sitemap; changing a slug stores the former slug for a redirect; meaningful product edits update `contentUpdatedAt`.

The product list now has a dedicated SEO status column and a server-side **Needs SEO** filter. Each row shows **Ready** or the number of issues with the first reason; the filter sends `seo=attention`, which uses the same rules as the publish gate and Product JSON-LD inputs. The **View public page** action uses the product's canonical slug rather than its UUID. The product editor now has a publish gate and a post-publish verifier:

- Browser-side checks require product name, SKU, category, a product-specific description of at least 50 words (about 300 characters), SEO title (1–70 characters), SEO description (80–160 characters), one verified model/MPN/IMPA identifier, and a main image with alt text.
- The backend independently checks these requirements, exact duplicate descriptions among published products, and SKU/category presence. Single-item and bulk publishing return field-level errors; bulk publish rejects the entire selected batch if any selected item fails.
- After a successful publish save, the admin browser fetches the public canonical URL (up to three attempts) and checks HTTP success, exact canonical, matching H1, and Product JSON-LD. A failed check leaves the form open and reports that the record was saved as published but public verification failed. It does not silently claim the page is live.
- Bulk publish is gated but does not yet run a public-route verifier per row. The post-publish verifier is currently in the single product editor flow.
- Duplicate detection now normalizes Unicode compatibility forms, whitespace, and case, then blocks exact normalized matches only. The product editor has an explicit override checkbox for legitimate variants; the flag is request-only and is not stored as product data.
- Bulk-publish field errors now include the product SKU and field in the backend response and are displayed as a per-product list in the admin product list.
- Internal search terms (`seoKeywords`) are never rendered into product HTML, a meta keywords tag, or hidden text; they are used only by storefront search. The old hardcoded homepage meta keywords tag was removed.
- Product JSON-LD and the Merchant Center feed validate GTIN as GTIN-8/12/13/14; empty or malformed values (including IMPA codes) are omitted.
- CSV import previously accepted a `status` column and defaulted missing status to `published`, bypassing the publish gate. It now always creates drafts regardless of CSV status.

Remaining optional work:

1. Add a CSV export of the **Needs SEO** result so the catalogue team can work through issues offline; the list filter itself is already authenticated, paginated, and server-side.
2. Avoid a manually maintained “submit URL” list. The dynamic sitemap should always derive from the same published product set. Search Console submission is a site-level step after deployment, not per-product admin entry.
3. An explicit `indexingEnabled` field should only be introduced if the business needs a noindex-but-published state. If added, apply it consistently to the public response, sitemap, and admin audit; do not let these three sources disagree.

## Brand and category hubs

The repository previously had one general `/brands/` directory and product filtering by brand/category query parameters, but no dedicated indexable hub per entity. Workspace changes now add `/en/brands/{slug}/` and `/en/categories/{slug}/` routes, server-rendered headings/copy/product links, React hub pages, and crawlable brand links from the brand directory. Admin brand and category forms now expose SEO title/description, visibility, description-length counters, and an indexability badge. Renaming a brand or category keeps its existing URL; only an explicit slug edit changes it, and the previous URL 301s to the current one. Industry SEO/visibility fields are stored in admin for the future industry directory/detail page (there is no standalone industry URL yet). Brand/category detail APIs return up to 24 published products for these pages.

Hubs are intentionally noindex and excluded from the sitemap until they have at least one published product, an authored description of at least 120 characters, an SEO title, and an SEO description of at least 80 characters. Over-length titles/descriptions are shown in admin as warnings, not blockers, because the server does not noindex for length. The sitemap builder and storefront hub service call the same `backend/src/utils/hubSeo.ts` predicate, and `server.js` trusts the API-returned `indexable` flag, so a hidden hub (404) can never remain in the sitemap. Industry entries are directory-only; the sitemap emits no `/en/industries/:slug/` URLs. These thresholds are an editorial launch gate, not a Google ranking guarantee. Category internal links from all category navigation surfaces have not yet been comprehensively converted; the dedicated hub route and child-category links exist.

## Problems found and code corrections made

| Finding | Evidence / impact | Workspace correction |
|---|---|---|
| Static middleware preceded the sitemap route | A static file could shadow `/sitemap.xml`; root could also be served before redirects | SEO routes now precede `express.static`; directory index and redirect behavior are explicit |
| Express 5 rejected the product route pattern | `:locale(en|ar|es)` throws a `path-to-regexp` error at server startup | Replaced with a supported route plus a locale allow-list |
| The build created a second sitemap | A `public/` file or Vite output could become the served sitemap and diverge from the database | Removed `public/sitemap.xml` and removed static sitemap generation from the production build |
| Slash conventions disagreed | Production redirects `/en/products` to `/en/products/` | Redirects, canonicals, structured data URLs, sitemap, previous-slug redirect, and Merchant Center URLs now use trailing slashes |
| Untranslated locales could be indexed | English shell content was returned for `/ar/` and `/es/` | Server emits both `X-Robots-Tag: noindex, follow` and an HTML noindex meta; client SEO also checks locale; hreflang is removed |
| Migration would stamp existing rows with the migration time | A default of `CURRENT_TIMESTAMP` on add would assign nearly identical `lastmod` values | Migration adds nullable, backfills from `updated_at` then `created_at`, and only then sets NOT NULL/default |
| Old-slug redirect lacked slash | API redirect target could cause an extra slash redirect | Updated target to the current canonical trailing-slash product URL |
| Build-time API fetch could wait indefinitely | Build and SEO audit can hang if the API is unreachable | Product fetch uses a 12-second abort timeout and safely returns no products |
| Product listing canonical lacked locale prefix | Filter canonical could point to `/products` instead of the locale route | Product list now constructs its canonical under `/{locale}/products/` |
| Admin could claim publish succeeded before checking the public URL | API save success did not prove the public route returned product HTML | Added server-side publish requirements, structured failure details, and browser verification of HTTP/canonical/H1/Product JSON-LD |
| Brand/category only had listing/filter URLs | No distinct authored landing pages existed for specific brands/categories | Added SSR/React entity hubs, product data on hub APIs, brand directory links, SEO fields in admin, and eligibility checks in the dynamic sitemap |
| Workspace robots lost the admin rule | Admin path had no crawl block in source robots | Restored `Disallow: /admin` while retaining `/api/`, checkout/account blocks, and sitemap line |
| Product/hub 404s could be cached before publication | A negative response could persist at a shared cache | Product and hub not-found responses now send `Cache-Control: no-store` in the workspace; production currently returns 200 SPA shell for fake paths, so this fix is not live yet |
| A stale API sitemap omitted a real static route | The live API sitemap returned 12 static URLs and omitted `/en/intelligence/`, so the frontend would advertise fewer pages than it served | `/sitemap.xml` now merges any missing static English routes into a valid API sitemap; if the API is unavailable it serves a complete 13-route XML fallback |
| API outages produced misleading 200 shells | A product or hub request during an API failure returned an empty SPA page with indexable metadata | Product/hub render failures now return HTTP 503, `Retry-After: 300`, `X-Robots-Tag: noindex`, and a noindex HTML shell |
| React 19 left prerendered head tags in place | `react-helmet-async` 3 renders native tags but does not remove server `data-rh` tags, producing duplicate titles/canonicals after hydration | `reconcilePrerenderedHead()` removes a prerendered tag only when a live equivalent key or JSON-LD type exists, preserving server-only schemas |
| Homepage JSON-LD used non-canonical URLs | WebSite URL lacked `/en/`, CollectionPage URL lacked a trailing slash, and SearchAction targeted `/en/products?search=` | Client JSON-LD now uses `/en/`, `/en/`, and `/en/products/?search={search_term_string}` |
| Translated hub routes returned 404 | The static-route predicate matched `brands`/`categories` before their dynamic two-segment forms, so `/es/brands/abb/` was rejected instead of served noindex | Dynamic prefixes are resolved before the static directory match; translated hub shells stay reachable with noindex |
| Empty-cart checkout redirected to a non-canonical URL | `/en/checkout/` navigated to `/en/products` without a trailing slash, adding a redirect hop | Checkout now navigates through the localized path helper, producing `/en/products/` or `/ar/products/` |

## Deployment gates

The public site can be discovered before deployment because `robots.txt` advertises its sitemap and inbound links can trigger crawling. The old 39-URL sitemap and SPA behavior are still live, so deploy promptly rather than treating indexing submission as the first moment Google can see the site.

### Six readiness gates from the follow-up review

1. **Runtime:** after deployment prove root → `/en/` with one 301, unknown product/hub → true 404 with `Cache-Control: no-store`, `/ar/` and `/es/` → noindex meta and header, and `/sitemap.xml` → current XML with no `priority`, `changefreq`, or `hreflang`, containing all 13 static English routes. Check the `X-Sitemap-Source` header: `api`, `api+static-merge`, or `static-fallback`. Simulate an API outage and confirm product/hub responses are 503 with noindex, not indexable 200 shells. If any fails, the new server code is not live and the rest of launch validation is premature.
2. **All 13 static pages:** inspect raw HTTP/View Source, not only the hydrated DOM. Each should have unique title/description, exactly one self canonical, one H1, substantive page-specific copy, and anchor links with hrefs for navigation and footer. The prerenderer now emits two page-specific paragraphs, breadcrumb navigation, primary navigation, and footer links before React runs. Home JSON-LD should contain accurate Organization and WebSite identity details and canonical `/en/` URLs. Inspect Arabic/Spanish raw HTML for noindex and no hreflang too. Do not treat the local SEO audit as a substitute for inspecting each generated response.
3. **Host variants:** test HTTP/HTTPS, www/apex, and slash/non-slash forms for representative pages. Require one 301 to the same canonical final URL with no chain. HTTP apex currently redirects to HTTPS apex. `www.alkatraders.co` did not resolve from the audit workstation; its DNS and redirect behavior remain unconfirmed. A 200 duplicate needs a redirect.
4. **Quality basics:** PageSpeed Insights mobile on home and a catalog page when available; check severe LCP/layout shift, useful image alt attributes, a real 404, and substantive accurate privacy/terms/refund content.
5. **Catalog:** currently zero products by design; don't publish a placeholder. With the first genuine listing, verify Admin's publish gate and public verifier, API count, product HTML/JSON-LD, Rich Results Test and sitemap `lastmod`. Keep the item published only if it's a genuine listing. Enter data in the Railway production admin/API, not Neon. Scale genuine inventory in batches of about 30–50; do not wait for a complete catalog to submit the sitemap.
6. **Search Console:** verify the Domain property by DNS now. After Gates 1–4 pass and `/sitemap.xml` is the new XML, submit it even if only static pages exist. Inspect home and a catalog page; inspect the first product when available. Request indexing for only a few representative URLs.
