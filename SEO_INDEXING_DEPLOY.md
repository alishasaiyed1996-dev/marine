# SEO indexing rollout

This change updates the product URL scheme, product metadata, runtime sitemap, and frontend response handling. The canonical URL policy uses trailing slashes because the production host currently redirects directory-style URLs to that form. **Two** migrations are pending: `20261019000000_product_seo_url_history` and `20261021000000_hub_slug_history`. Apply both, in order, before deploying the backend code that reads the new fields/tables. The production site is already crawlable, so Google may fetch the old sitemap before rollout; prioritize replacing the old behavior promptly.

## Six rollout gates

The live site is public and `robots.txt` already advertises the sitemap, so Google can crawl it before this rollout. Treat readiness as something to reach quickly. The current live site still serves the old 39-URL sitemap and old SPA fallback behavior; prioritize deploying the fixed code.

### Gate 1 — prove the new runtime is live

Using Googlebot user agent and raw HTTP responses, verify `/` is a 301 to `/en/`, an unknown product/hub URL is a true 404 with `Cache-Control: no-store`, `/ar/` and `/es/` carry noindex in HTML and `X-Robots-Tag`, and `/sitemap.xml` is the new XML without `priority`, `changefreq`, or `hreflang` and contains all 13 static English routes. Check `X-Sitemap-Source`: `api`, `api+static-merge`, or `static-fallback`. Confirm the raw `/en/` HTML already carries the admin site SEO title/description (not just after hydration), and that `og:title`/`og:description`/`twitter:title`/`twitter:description` match it. There must be no `<meta name="keywords">` anywhere. **The sitemap must contain no `/en/industries/<slug>/` URLs** — industries are directory content only. Simulate an API outage and confirm product/hub responses are 503 with noindex, not indexable 200 shells. Stop the remaining SEO launch checks if these fail; those results mean the intended route handlers are not serving production. The workspace removes the old static sitemap and handles `/sitemap.xml` dynamically, merging missing static routes into the API response and falling back to the complete 13-route static XML if the API is unavailable.

### Gate 2 — inspect all 13 static pages as raw HTML

For each intended English static URL, use `curl`/View Source (not DevTools' hydrated DOM) and check: a unique title, unique meta description, exactly one self-referencing canonical, one H1, substantive page-specific body copy, and crawlable internal links. Navigation/footer links should be `<a href="…">` anchors. The prerenderer emits two page-specific paragraphs, breadcrumb navigation, primary navigation, and footer links before React runs; confirm this in each generated response rather than assuming it from the build log. Confirm the home page has Organization and WebSite JSON-LD with accurate public company name, logo, address (only if public), contact details, and canonical `/en/` URLs. Check the Arabic and Spanish raw HTML too: noindex, no hreflang, and accurate page/head details. Do not claim this gate passed from the local SEO audit alone; inspect each generated response.

### Gate 3 — consolidate host and slash variants

Check HTTP and HTTPS, `www` and apex, plus trailing-slash and non-slash variants for representative pages. Each variant should reach one final canonical URL with one 301 and no redirect chain. HTTP apex currently returns a 301 to HTTPS apex. `www.alkatraders.co` did not resolve from the audit workstation, so its behavior is still unknown; confirm DNS and test before declaring this gate passed. If `www` serves a 200 site copy, configure a redirect to the apex host.

**Renamed URL checks.** For a product, category and brand that has been renamed, request the old URL and inspect the first response only:

```bash
curl -sI "https://alkatraders.co/en/product/OLD-SLUG/" | grep -iE '^(HTTP/|location:)'
```

- Expect exactly one `301` with `Location` pointing straight at the current canonical URL, never `/slug-history/…` and never an intermediate slug.
- If a product was renamed twice (A → B → C), request A and confirm it lands directly on C. The history table points at the product/category/brand row, so it resolves to the current slug; do not accept a chain A → B → C.
- Repeat for `/en/categories/OLD-SLUG/` and `/en/brands/OLD-SLUG/`.
- Check the no-trailing-slash variant also returns one 301 directly to the final canonical URL.

### Gate 4 — content and page-quality basics

Run PageSpeed Insights mobile checks for the home page and a catalog page when one exists. Look for severe LCP or layout-shift failures, confirm images have useful alt text, check a real 404 response/page, and read the privacy, terms, and refund pages for substantive and accurate content. A perfect PageSpeed score is not a launch requirement.

### Gate 5 — catalog data (pending real products)

There are currently **no listed products**, as confirmed by the owner; the live storefront API's zero count is expected. Do not create a placeholder solely for SEO validation. When a genuine product is first listed, publish it through the production admin and verify the publish gate, post-publish verifier, storefront API count, product-specific raw HTML and Product JSON-LD, and sitemap entry with sensible `lastmod`. The publish gate requires at least 50 words (or roughly 300 characters) of product-specific description, a 1–70 character SEO title, an 80–160 character SEO description, a verified model/MPN/IMPA, an image, and main-image alt text. Validate its structured data with Google's Rich Results Test. Confirm an empty or malformed GTIN is absent from both the Product JSON-LD and the Merchant Center feed — never send an IMPA code as `gtin`. Then keep it live only if it is genuinely for sale; otherwise unpublish it. Confirm product entry is happening in the production Railway-backed admin/API, never local Neon. Once the first real product pipeline is verified, add catalog inventory in batches of roughly 30–50 quality listings; no need to wait for the whole catalog before sitemap submission.

### Gate 6 — Search Console

Verify the Search Console Domain property by DNS now; this does not depend on code deployment. After Gates 1–4 pass and the sitemap is the new valid XML, submit it even if the catalog is still empty (the eligible static pages can be crawled). Run URL Inspection on the home page and a catalog page; inspect a product once a genuine product exists. Request indexing for only those few important URLs, not in bulk.

## Rollout order

1. Confirm the production project/environment, `api` service and `Postgres` resource, and domain-to-service mapping. This has been checked: both domains terminate at Railway; API database host is `postgres.railway.internal`. Do not use local Neon for this rollout.
2. Take and verify a restorable backup of Railway Postgres before migration. Railway documents volume backups (manual or scheduled) and logical `pg_dump` backups; verify that a snapshot or backup exists and that it can be restored in this project's Backups tab. If you also need a portable dump, use Railway CLI's `railway connect postgres --tunnel-only` where possible, or a temporary TCP proxy, then confirm the dump is readable and close the tunnel/disable the proxy. Do not expose the database publicly as a permanent endpoint. The current dashboard state/plan entitlements have not been inspected, so backup availability for this exact project is not yet confirmed.
3. Confirm **both** pending migrations are applied: `20261019000000_product_seo_url_history` and `20261021000000_hub_slug_history`. The Railway IaC configures `preDeploy: "npx prisma migrate deploy"` for the API service. Railway runs pre-deploy commands between build and start, with service variables and private networking, and a failing command prevents deployment. Apply the updated IaC and verify the API deployment's pre-deploy setting. Alternatively, open a shell in the API service and run the migration once before deploying the new backend. Do not use workstation `railway run` for the migration and do not run `migrate dev`. Critically, `backend/.env` on this workstation points at Neon, which is **not production**: running `migrate deploy` from the workstation can succeed against Neon and give false confidence while Railway Postgres remains un-migrated. Only the Railway pre-deploy run (or a shell inside the Railway API service) counts. The migrations are additive (`content_updated_at`, product slug history, and category/brand/industry slug history), but a backup is still required.
4. Deploy the API service after the migration. Its new code reads the additive fields and serves the dynamic sitemap at `/api/v1/sitemap.xml`.
5. Deploy Railway frontend service `marine` after the API. Railway status and live response headers confirm this service answers for `alkatraders.co`; Hostinger `.htaccess` is not in the request path. Workspace IaC pins `npm run build` and `npm start` (`node server.js`); after applying it, verify the resulting deployment metadata/start logs show those commands and the server listening line. The root build creates `frontend/dist`, prerenders HTML, and copies it to `frontend-dist`; confirm the runtime image contains `frontend/dist/index.html` (health response reports `build:present`).
6. Run Gates 1–4 above against production. The product-specific portions of Gate 5 are explicitly pending until real products are listed.
7. Submit the new sitemap after the technical gates pass; its static English pages remain useful while the catalog is empty. Then complete Gate 5 when genuine inventory is entered and use Search Console for a few representative URLs.

## Environment and operational notes

- Set the `marine` service's public `VITE_API_URL=https://api.alkatraders.co` as a variable available during the **build** as well as runtime. The build-time helper `scripts/fetch-products.mjs` reads `SEO_API_BASE` (defaulting to `https://api.alkatraders.co`) while prerendering. Railway's private network is unavailable during builds, so never set the build-time API origin to `postgres.railway.internal`, an internal Railway hostname, or an unset value that points at the storefront. An unreachable API currently logs a warning and silently continues with zero product prerenders; this is safe while the catalog is intentionally empty but would hide catalog pages if products are added later. `server.js` fetches product data at request time using the API origin; therefore a product entered after build can render without rebuilding, provided the live API has that product and the frontend's public API origin is correct.
- `server.js` uses `VITE_API_URL` or defaults to `https://api.alkatraders.co`; it strips an optional `/api/v1` suffix and requests the backend directly. Do not use the public storefront origin: its `/api/v1/*` path is served as frontend HTML. The client bundle expects `VITE_API_URL` to be the API **origin** (for example `https://api.alkatraders.co`); the client appends `/api/v1` itself. Setting the value with `/api/v1` produces duplicated client paths.
- Prerendered requests receive a complete SEO head, and React 19 + `react-helmet-async` 3 renders new head tags natively without removing server `data-rh` tags. `src/components/seo/reconcileHead.ts` removes a prerendered title/canonical/meta/JSON-LD only when a live equivalent key or JSON-LD type exists; server-only schemas remain. Re-run hydration checks after changing SEO components.
- The homepage now reads `site.seoTitle` / `site.seoDescription` in three places that must agree: the build-time prerender (`scripts/prerender.mjs`), the request-time Express shell (`applySiteSeo()` in `server.js`), and the hydrated React page (`Home.tsx` via `useStoreSettings`). Express patches the prerendered `/en/` head with the same public settings endpoint, so Google and social scrapers see the configured title/description without executing JavaScript. If settings change, the effect is visible after the API cache expires (about 60 seconds) and the next request; no frontend rebuild is needed.
- Hub indexability is computed once in `backend/src/utils/hubSeo.ts`. The sitemap builder and the storefront brand/category services (which return `indexable`) both call it, and `server.js` plus the React hub pages trust that returned flag. Do not re-create the predicate in a fourth place. A hidden hub is a 404 and cannot enter the sitemap. Industry entries are directory content only, so the sitemap must never emit `/en/industries/<slug>/` URLs.
- Product publish rules are enforced server-side in `backend/src/services/productMutations.ts` and mirrored in the admin form. Description minimum: 50 words or roughly 300 characters. `seoKeywords` / internal search terms are never rendered into HTML or a meta keywords tag; they are only used by the storefront search index.
- `/sitemap.xml` keeps the API sitemap as the source of truth, merges any missing static English routes, and returns a complete 13-route fallback XML when the API is unreachable. The `X-Sitemap-Source` response header reports `api`, `api+static-merge`, or `static-fallback`.
- Product and hub render failures return HTTP 503 with `Retry-After: 300`, `X-Robots-Tag: noindex, follow`, and a noindex HTML shell. This prevents crawlers from indexing an empty page during a transient API outage.
- The build produces **13 English static route documents plus the base Vite shell (14 HTML files)**; the runtime sitemap targets those 13 routes plus published products and eligible hubs. `/en/intelligence/` is included in the static route set.
- Database fields are additive: `products.content_updated_at`, `product_slug_history`, `category_slug_history`, `brand_slug_history`, and `industry_slug_history`. The migration does not change current product status values or IDs.
- Product HTML and the dynamic sitemap currently index English only. Arabic and Spanish routes remain available through the SPA but are marked noindex in both HTML and `X-Robots-Tag` until translated content and reciprocal alternates are implemented. No hreflang is emitted while equivalent translations are unavailable.

- The legacy source sitemap was removed. ## Rollback

The database migration is additive. To roll back application behavior, redeploy the prior frontend and API builds. Keep the added columns/tables (content timestamp and slug-history tables) until the previous code is stable; they are not destructive and can be removed later in a separate reviewed migration.
